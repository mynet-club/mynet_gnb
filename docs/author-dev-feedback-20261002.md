## 1. 热更新失败时可能进入半停机状态

当前热更新流程大致是：

```text
停止旧 gnb core
卸载旧共享内存
将 map 改名为 .old
重新读取配置
创建新 gnb core
```

问题在于，旧 core 已经停止后，只要以下任一步失败：

- 共享内存重新打开失败；
- 配置读取失败；
- 新 core 创建失败；
- 新 core 初始化失败；

旧 core 就不能继续提供服务。当前代码在部分失败路径中直接返回或退出，缺少恢复旧 core、恢复旧 map 的回滚路径。

这里的失败原因不应默认理解为“内存不足”。如果只是一次普通配置热更新，创建新 core 所需的额外内存通常有限，内存不足大概率不是常态原因。更值得关注的是共享内存重映射、配置错误、资源打开失败或初始化路径异常。

因此这个问题的重点是失败处理顺序：旧 core 已经停止后，任何初始化失败都可能让服务进入半停机或直接退出。当前代码缺少清晰的恢复路径，应该在后续测试中重点观察。

## 2. secure-index worker 的退出标志需要逐个核对

公共等待逻辑会等待：

```c
worker->thread_worker_run_flag == 0
```

作者快照中，`secure_index_worker` 的线程入口将 `thread_worker_run_flag` 设为 `1`，但退出循环后没有明确设回 `0`。如果停止流程等待这个标志，可能一直停在：

```text
WAIT worker [...] stoped...
```

这个问题只影响实际启用了 secure-index/index worker 的运行模式。如果节点不启用 index 功能，该 worker 不会启动，通常不会触发这个等待路径。但代码本身仍存在退出标志不对称，不能把“不启用该功能”当作代码已经修复。

在 MyNet 的实际部署中，应按功能开关区分验收：不启用 index 的节点验证普通热重启；启用 index 的节点再验证 worker 是否能够正常退出。

## 3. 热日志触发接口需要确认是否真正接通

作者快照新增了 `core.log.*` 控制项和 `log_trigger`，但需要确认主循环是否完整处理触发标志：

```text
读取 log_trigger
关闭旧日志 fd
重新打开日志文件或 UDP 日志
更新配置
清除 log_trigger
```

如果只写入共享内存而没有消费触发标志，`gnb_ctl` 命令会返回成功，但运行中的 gnb 不一定已经切换日志配置。

建议增加一个统一的日志重载函数，并验证：

- 切换日志目录；
- 切换 console/file/UDP level；
- 连续多次切换；
- 切换失败时旧 fd 仍可用；
- 热重启后配置是否按预期保留；
- fd 数量是否持续增长。

## 4. 共享内存 ABI 与 MyNet 发布流程

作者快照修改了 control block、conf zone、core zone 等结构。这个风险在 MyNet 的发行流程中由 workflow 统一构建和打包 `gnb`、`gnb_ctl`、`gnb_es`、`gnb_crypto`，因此不会把不同构建的程序混装发布。

这里保留这条记录的目的，是说明作者开发线改变了共享内存布局，后续升级时应把四个程序作为一个整体重新构建和验收；它不是当前 MyNet 发布流程中的待修复问题。

## 6. MyNet 补丁维护约定

MyNet 不会把不同作者基线的 proxy 实现强行合并成一个补丁。

每个作者基线都单独保存。当前每条基线只有一个 MyNet 补丁，统一命名为 `p1-route-proxy`：

```text
作者基线 A
  └── p1-route-proxy A

作者基线 B
  └── p1-route-proxy B
```

proxy 补丁允许因上游结构变化而不同。每次作者更新后，先导入新的固定基线，再重放、修改并验证该基线对应的 proxy 补丁。补丁目录必须记录：

- 作者来源和完整 commit 或快照 SHA256；
- 补丁适用的基线提交；
- 应用顺序；
- 编译和单元测试结果；
- 尚未完成的真实数据面测试。
